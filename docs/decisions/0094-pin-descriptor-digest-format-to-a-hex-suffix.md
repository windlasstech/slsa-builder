# Pin the Descriptor Digest Format to a Hex Suffix

## Context and Problem Statement

ADR 0092 accepted optional integrity digests in package-manager descriptors and deferred two axes:
the algorithm set and the digest format. ADR 0093 pinned the algorithm set to the W3C SRI token set
(`sha256`, `sha384`, `sha512`). This ADR decides the remaining axis: how the digest is written in
the descriptor.

Two structural constraints bound the choice:

- The digest rides in the SemVer build-metadata position of the descriptor (`name@version+suffix`),
  whose identifiers admit only `[0-9A-Za-z-]`. SRI base64's `+`, `/`, and `=` characters are illegal
  there, so an `algorithm-<base64>` suffix is not a grammatically valid descriptor for the top-level
  `packageManager` field, and Corepack — which parses the descriptor with `semver.valid` — cannot
  read it either.
- For as long as Corepack is the production provisioning path, the descriptor must be meaningful to
  the whole toolchain chain. Corepack parses and validates exactly the `algorithm.<hex>` form (and
  auto-generates it via `corepack use`); pnpm strips any suffix regardless of form; Yarn's binary
  ignores both fields. The actual consumers of the format are Corepack and the builder.

In what form is a declared digest written?

## Decision Drivers

- One descriptor, valid everywhere: the same manifest value must work for local Corepack
  development, the package managers, and the builder's reconciliation.
- Grammatical validity: the descriptor must remain valid SemVer and parseable by the provisioning
  layer.
- Canonical form: exactly one accepted representation per digest, so comparison is byte-exact and
  the grammar stays closed — no competing spellings of the same value.
- Honest ergonomics: acknowledge the SRI copy-paste friction and mitigate it with guidance, not with
  a second grammar.

## Considered Options

- Pin the format to the Corepack-style `+algorithm.<hex>` suffix in both manifest fields.
- Pin the format to the SRI `algorithm-<base64>` suffix.
- Accept both formats and sniff per descriptor.
- Add a devEngines-only `integrity` member for SRI-form digests while the top-level field uses the
  hex suffix.

## Decision Outcome

Chosen option: "Pin the format to the Corepack-style `+algorithm.<hex>` suffix in both manifest
fields", because it is the only form that is grammatically valid SemVer, readable by Corepack during
the provisioning window, auto-generated by the ecosystem's own tooling, and trivially computable by
consumers — while the SRI form fails every one of those constraints at the position the descriptor
occupies.

### The digest format

- Both manifest selection sources carry the optional digest as a `+algorithm.<hex>` suffix on the
  exact version: `packageManager: "yarn@4.18.1+sha512.<hex>"` and
  `devEngines.packageManager.version: "4.18.1+sha512.<hex>"` alike, per ADR 0091's uniform-source
  rule.
- The algorithm token is exactly one of `sha256`, `sha384`, or `sha512` (ADR 0093).
- The digest is written in hexadecimal. Surface rules — letter-case handling, length validation, and
  single-versus-multiple digest suffixes — are specification-level decisions and are not pinned
  here. A suffix that is not an `algorithm.<hex>` pair — including SRI `algorithm-<base64>` forms —
  is rejected before install with a dedicated diagnostic, registered in the specification phase.
- Consumers copying npm registry `dist.integrity` values must convert base64 to hex; the README and
  the format-rejection diagnostic carry a one-line conversion recipe.
- With the algorithm set (ADR 0093) and the format (this ADR) both pinned, no axes from ADR 0092
  remain deferred, and the specification phase can state the complete descriptor digest grammar.

### Confirmation

This decision is confirmed when:

- the JS/TS npm build-and-pack specification pins the `+algorithm.<hex>` suffix grammar for both
  manifest fields, including the surface rules this ADR leaves to the specification level;
- the format-rejection diagnostic is registered with specification parity;
- the fixture corpus covers accepted digests in all three algorithms and rejected uppercase,
  wrong-length, SRI-form, unknown-algorithm, and multi-suffix declarations, from both manifest
  sources;
- the README support-window section documents the declaration form and the base64-to-hex conversion
  recipe;
- a live verification runs a digest-declaring consumer through the Corepack provisioning path,
  proving the descriptor works end to end in the window.

## Pros and Cons of the Options

### Pin the format to `+algorithm.<hex>` (chosen)

- Good, because one descriptor serves the whole toolchain chain: Corepack validates it, pnpm strips
  it, Yarn ignores it, and the builder reconciles it — no consumer maintains two forms.
- Good, because it is valid SemVer by construction and matches what `corepack use` already
  generates, so consumers can adopt it without hand-computing anything.
- Good, because a single canonical format keeps comparison byte-exact and the grammar closed.
- Bad, because npm registry `dist.integrity` values (SRI base64) cannot be pasted directly and need
  a one-line conversion per version bump.

### Pin the format to SRI `algorithm-<base64>`

- Good, because registry integrity values could be copied verbatim.
- Bad, because base64 characters are illegal in SemVer build metadata: the top-level
  `packageManager` field cannot carry it at all, and Corepack rejects the descriptor during the
  provisioning window — the builder would accept a descriptor its own provisioning layer cannot
  read.

### Accept both formats

- Good, because consumers choose their preferred spelling.
- Bad, because the SRI form still fails in the top-level field, collapsing "both" into an asymmetric
  grammar with doubled spec, diagnostic, fixture, and fuzz surface for no reachable benefit.

### devEngines-only `integrity` member plus hex suffix

- Good, because SRI-form digests gain a legal home in one of the two fields.
- Bad, because it breaks ADR 0091's uniform-source rule with an asymmetric grammar, expands the
  closed `devEngines.packageManager` member set into unverified interoperability territory with
  npm's and pnpm's own devEngines parsing, and the top-level field still ends up hex-only.

## More Information

- SemVer 2.0.0 build-metadata grammar: <https://semver.org/#spec-item-10> — identifiers comprise
  ASCII alphanumerics and hyphens only.
- Corepack descriptor hash behavior: <https://github.com/nodejs/corepack#when-authoring-packages>
  and `sources/corepackUtils.ts` — the `algorithm.<hex>` form, validated over downloaded bytes;
  `corepack use` serializes `${algo}.${actualHash}` with SHA-512 by default (verified against
  Corepack 0.36.0, 12026-10-08).
- W3C Subresource Integrity: <https://www.w3.org/TR/sri/> — the `algorithm-<base64>` form used by
  npm `dist.integrity`.
- Base64-to-hex conversion recipes for the README and diagnostic (all commands verified on
  12026-10-08). For a pnpm pin, read the npm registry integrity value and convert:
  - npm:
    `npm view <pkg>@<version> dist.integrity | sed 's/^sha[0-9]*-//' | base64 -d | xxd -p -c 256`
  - pnpm:
    `pnpm view <pkg>@<version> dist.integrity | sed 's/^sha[0-9]*-//' | base64 -d | xxd -p -c 256`
  - Yarn Berry:
    `yarn npm info <pkg>@<version> --json | jq -r .dist.integrity | base64 -d | xxd -p -c 256`
    (Berry's `--fields` filter does not accept dotted paths)

  For a Yarn pin during the Corepack window there is no registry integrity value to convert: the
  executed distribution is the `repo.yarnpkg.com` bundle (per ADR 0070), so hash the download
  directly —
  `curl -sL https://repo.yarnpkg.com/<version>/packages/yarnpkg-cli/bin/yarn.js | shasum -a 512 | cut -d' ' -f1`.

- pnpm strips the descriptor suffix before version validation regardless of form
  (<https://github.com/pnpm/pnpm/commit/302a2f7d2cd68c0e7e2404418cffb4a7e406597>); Yarn's binary
  ignores both fields (verified on 4.18.1) — binary behavior is format-agnostic, so the format
  decision serves Corepack and the builder.
